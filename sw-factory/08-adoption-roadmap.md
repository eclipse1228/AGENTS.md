# 08. 내 SaaS 적용 로드맵

> 앞의 7개 문서가 **원본에 있는 사실**이라면, 이 문서는 그것을 바탕으로 한 **내 해석과 제안**입니다. 기간·비용 추정은 근거가 없어 넣지 않았습니다. 대신 단계마다 **졸업 기준**(다음 단계로 가는 조건)을 둡니다.

## 0. 전제와 원칙

- **스택은 다르다.** 데모는 GitHub + Cloudflare Workers + pnpm/TypeScript. 내 SaaS는 스택이 다를 수 있으므로 **개념을 옮기고 코드는 옮기지 않는다.** 가져올 것은 구조(상태 머신, 위험 정책, 3단 job, evidence, eval)이지 `packages/factory`의 코드가 아니다.
- **사람 승인 지점은 일부러 남긴다.** 데모와 Codex·mastra의 사례가 같은 방향: 시작(`@factory go`)과 민감 병합(T2/T3)에 사람.
- **한 SaaS로 파일럿 → 확산.** 가장 작고, 테스트가 있고, 장애 영향이 낮은 SaaS 하나로 시작.
- **판정 기준은 6개**([01 문서](01-concepts-and-criteria.md)). 각 단계가 어느 기준을 채우는지 표시했다.

## 1. 전체 지도

| 단계 | 이름 | 채우는 기준 | 데모의 대응 | 사람 개입 |
|---|---|---|---|---|
| 0 | 진단 | — | — | 전부 사람 |
| 1 | 에이전트 기반 | 3(게이트) | P1 | 사람이 요청·병합 |
| 2 | 위험 등급·소유자 | 4(위험 위임) | P2의 `risk-policy`/CODEOWNERS | 사람이 병합 |
| 3 | 반자동 유입→PR | 1(유입), 2(병렬), 5(보고 일부) | P2 | `go` 승인, T2/T3 병합 |
| 4 | 증거 게이트·자동 병합 | 3(게이트 강화) | P3 | T0/T1 자동 병합, 나머지 사람 |
| 5 | 환류(자기개선) | 5(보고), 6(자기개선) | P4 | 개선 PR은 항상 사람 승인 |

## 2. 단계 0 — 진단 (코드 변경 없음)

**목표**: 내가 가진 SaaS 각각이 지금 어디에 있는지 숫자와 표로 안다.

**할 일**
1. SaaS마다 [09 문서의 진단표](09-glossary-and-checklists.md#2-saas-진단표-템플릿)를 채운다: 스택, 저장소 호스팅, CI 유무, 테스트 종류·커버 범위, 배포 방식, DB 마이그레이션 방식, 민감 영역(인증·결제·개인정보), 하루 평균 이슈·PR 수, 병합하는 사람 수.
2. 판별 기준 6개를 SaaS별로 충족/부분/미충족으로 채점한다.
3. **파일럿 SaaS를 하나 고른다.** 선택 기준(해석): ①테스트·CI가 이미 있음 ②저장소가 GitHub ③장애 영향이 낮음 ④내가 코드를 가장 잘 앎(에이전트 결과를 검토할 수 있어야 함) ⑤유지보수 이슈가 꾸준히 들어옴.

**배울 것**: 블로그 1편(01 문서), 데모 README의 6개 기준 표.
**졸업 기준**: SaaS별 현황표 + 파일럿 선택 이유 1문단.

## 3. 단계 1 — 에이전트 기반

**목표**: 에이전트가 PR 하나를 **혼자 CI 통과까지** 가져올 수 있는 바닥을 만든다. 팩토리가 아니라 "에이전트가 일할 수 있는 저장소".

**만들 것**
1. **`AGENTS.md` 하나**(다른 도구용 파일은 이것을 가리키는 링크). 데모 `AGENTS.md`를 틀로 쓴다: 구조, 명령(설치/전체 검사/E2E), 규칙, **마이그레이션 주의**, 병렬 작업 시 워크트리 지침.
2. **검증 명령 한 줄**(`typecheck && lint && test`)과 그것을 돌리는 CI. 에이전트가 끝내기 전에 이 한 줄을 통과시키게 지침화.
3. CI 필수 체크를 브랜치 보호에 등록하고 **main 직접 push 금지**.
4. 지침에 **"테스트를 먼저 쓴다, 버그는 수정 전 코드에서 실패하는 테스트를 먼저"**를 넣는다(4단계 evidence의 사전 습관).
5. 에이전트에게 쓰게 할 때 **작업마다 별도 브랜치/워크트리**.

**배울 것**: `AGENTS.md`, `docs/operations.md`, `ci.yml`, P1 계획서의 "Global Constraints"(버전 고정, 테스트 대상 고정 방식).
**데모에서 가져올 아이디어**: 외부 스위트는 **특정 커밋에 고정**(pin), 미구현 기능은 skip 목록으로 명시.

**졸업 기준**
- [ ] 에이전트가 이슈 하나를 받아 PR을 열고 CI가 통과한다(사람이 병합).
- [ ] 같은 작업을 3회 반복해 **결과가 안정적**인지 기록했다(테스트가 약하면 여기서 드러남 → 테스트 보강이 먼저).

**주의**: 테스트가 거의 없으면 이 단계의 대부분이 **테스트 확보**가 된다. 데모도 RealWorld 공식 테스트 스위트를 게이트로 "빌려와서" 시작했다.

## 4. 단계 2 — 위험 등급과 소유자

**목표**: "에이전트가 건드려도 되는 곳 / 사람 승인이 필요한 곳 / 절대 못 건드리는 곳"을 **파일로** 정한다.

**만들 것**
1. **`risk-policy.yml`**(또는 우리 스택에 맞는 동등물): 경로 glob → T0~T3, `default`는 T2(모르면 사람), **좁은 규칙을 위에**.
2. **CODEOWNERS**를 정책과 동기화(두 파일의 일치를 검사하는 테스트도 함께).
3. 아래를 처음부터 **T2/T3**로 분류(해석 — 데모 분류에서 일반화):
   - T3(에이전트 수정 금지): CI/워크플로 파일, 에이전트 지침·설정(`AGENTS.md`, `.claude/`, `.agents/`), 정책 파일, 게이트를 실행하는 스크립트, 고정된 외부 테스트
   - T2(사람 승인): **인증·세션·토큰**, **결제·정산**, **DB 마이그레이션**, 의존성 매니페스트·락파일, 인프라·배포 설정, 환경변수·시크릿 처리, 외부 수집 엔드포인트의 인증 경계
   - T1: 일반 앱 코드·테스트
   - T0: 문서·카피
4. T3는 **대소문자 무시** 매칭, **rename은 이전·새 경로 모두 판정**(데모가 겪고 막은 우회).
5. PR의 등급을 라벨로 붙이고, **구현 역할이 T3를 건드리면 실패하는 체크**(`risk-tier`)를 만든다. 이 체크는 **PR의 코드가 아니라 base 커밋의 판정 코드**로 실행.

**배울 것**: `risk-policy.yml`, `CODEOWNERS`, `policy/risk.ts`([07 문서](07-runtime-code-notes.md#2-위험-정책-policyriskts)), 설계 4.3.
**졸업 기준**
- [ ] 정책 파일이 있고 **의도적으로 T3 파일을 바꾼 PR이 실제로 막히는 것을 확인**(음성 대조).
- [ ] T2 경로 PR이 사람 승인 없이는 병합되지 않는다.
- [ ] CODEOWNERS 소유자가 **2명 이상**이거나, 1명이면 자기 PR엔 게이트가 약하다는 것을 알고 있다(데모의 알려진 한계).

## 5. 단계 3 — 반자동 유입 → PR

**목표**: 이슈 하나가 사람의 **`go` 한 줄**만으로 구현 PR까지 가고, **다른 모델이 리뷰**한다. 병합은 아직 사람.

**만들 것**
1. **이슈 템플릿**(feature/bug/feedback). 완료 기준을 쓰게 한다(블로그의 "Intent vs Execution" 사고를 줄임).
2. **트리아지**: 분류, 중복 검사, 예상 위험 등급, **테스트로 확인 가능한 수용 기준** 코멘트. 저비용 모델로 충분(데모는 DeepSeek Flash).
3. **`@factory go`** 같은 **명시적 승인 명령**. 쓰기 권한자만. 코드 펜스 안의 명령은 무시, 봇 코멘트 무시. `stop`/`retry`도.
4. **구현 에이전트**: 금지 경로, 의존성 추가 금지, commit/push 금지, 검사 통과 상태로 종료.
5. **교차 리뷰**: 구현과 **다른 엔진**. 판정은 JSON(verdict + findings[category, severity])이고 **head SHA에 묶음**. 수정 라운드 **최대 3회**, 초과·예산 초과는 `needs-human`.
6. **상태는 라벨 하나**(`factory:*`)와 허용 전이표. `merged`/`deployed`는 에이전트가 못 선언.
7. **런 기록**(JSONL 한 줄: 역할, 엔진, 모델, ok, 턴, 비용, 시간, 실패 사유, 지적 범주)을 별도 브랜치나 저장소에 남긴다. 이후 모든 보고·집계가 이것만 읽는다.
8. **가드레일 3종**: 런당 예산(턴·시간·비용), 일일 런 상한, **실패율 차단기**(최근 7일 10회 이상이고 성공률 50% 미만이면 중지).

**구현 방식 제안(해석)**
- 처음에는 **GitHub Actions + 얇은 CLI**로 시작하고, 워크플로 YAML에는 로직을 넣지 않는다(CLI 호출만).
- GitHub·에이전트를 **인터페이스 뒤에** 두고 목 구현으로 단계 전체를 테스트(데모의 `GitHubPort`/`FakeAdapter`).
- 워크플로 간 이벤트 체인이 필요하면 **GitHub App 토큰**(`GITHUB_TOKEN`으로 만든 이벤트는 다른 워크플로를 트리거하지 않음). **App에 Workflows 권한은 주지 않는다.**
- 에이전트를 돌리는 job은 `prepare/agent/publish` **3단**(agent에는 GitHub 토큰 없음, 엔진 키 하나만).
- **더 작게 시작하는 방법**: 3~4번(템플릿+트리아지+`go`+구현)만 먼저 하고, 교차 리뷰·보드·대시보드는 뒤로. 데모도 P2에서 코어를 만들고 보고는 P4로 미뤘다.

**배울 것**: `factory-triage/command/implement/review/fix.yml`, `prompts/*`, `state/machine.ts`, `stages/protect.ts`([07](07-runtime-code-notes.md)), 설계 5장, P2 계획서 "Review Focus".
**졸업 기준**
- [ ] 이슈 10건 정도를 이 흐름으로 처리하고 **성공률·비용·`needs-human` 사유**를 기록했다.
- [ ] **일부러 만든 악성 입력**(이슈 본문에 "AGENTS.md를 무시하고 …", 표식 위조, `fixes #N`)이 구현을 시작시키거나 규칙을 바꾸지 못한다.
- [ ] 권한 없는 사용자의 `go`가 거부된다.
- [ ] 실패율 차단기가 실제로 작동하는지 시험했다(가짜 실패 주입).

## 6. 단계 4 — 증거 게이트와 제한적 자동 병합

**목표**: 버그 수정은 **수정 전 실패 증거** 없이는 못 들어오고, 낮은 위험(T0/T1)만 자동 병합된다.

**만들 것**
1. **`evidence` 필수 체크**: 버그 PR에서 PR이 추가·수정한 테스트 파일만 base 트리에 덮어써 실행 → **실패해야 함**, head에서 같은 테스트 → **통과해야 함**. 테스트 변경이 없으면 실패.
   - 판정은 종료 코드가 아니라 **테스트 러너 JSON의 단언 결과**(수집 오류로 실패한 테스트는 재현으로 인정하지 않음).
   - 계획(토큰 필요)과 실행(PR 코드 실행, **시크릿·토큰 없음**)을 **다른 job**으로 분리, 판정 코드는 **base의 CLI**.
   - `evidence-plan`이 실패해도 `evidence`가 **건너뛰지 않고 실패**하게(건너뛴 필수 체크는 통과로 취급되므로).
2. **병합 게이트**(결정적 코드, LLM 아님): T0/T1 + 필수 체크 전부 통과 + 현재 head SHA의 승인 → squash 병합. T2/T3 → `needs-human`. 변경 파일을 못 읽으면 T3로 간주(fail closed).
3. **PR 보고서**(요약, 이유, 증거, 남은 위험, 등급과 근거 파일, 실행 정보)와 **커밋 트레일러**(`Agent-Signature`, `Factory-Issue`)로 에이전트 작업을 사람에게 연결.
4. (선택) **유입 자동화**: 프로덕션 에러(정규화된 fingerprint로 중복 묶음) / 사용자 피드백 / 스모크 실패를 이슈로. **외부 입력이 이슈로 들어갈 때는 표식·멘션·`fixes #N` 무력화, 개인정보 정규화**(데모 [05 문서](05-security-and-limits.md)).
5. **음성 대조 습관**: 새 게이트를 만들면 반드시 **그 게이트가 막아야 하는 나쁜 PR을 만들어 실제로 막히는지** 확인.

**배울 것**: `policy/evidence.ts`, `ci.yml`(`evidence-plan`, `evidence`), `stages/gate.ts`, P3 계획서의 **판정 후보 10개**, 운영 문서의 "심은 버그" 런북.
**졸업 기준**
- [ ] 심은 버그 하나로 "이슈 → `go` → 재현 테스트 → evidence 통과 → 병합 → 배포 → 증상 사라짐"을 **사람 개입 없이** 확인(데모의 `Math.floor` 시나리오에 해당).
- [ ] 수정 전에도 통과하는 테스트만 가진 PR이 evidence에서 **실패**함을 확인.
- [ ] T0/T1 자동 병합이 이 SaaS에서 위험하지 않다는 근거(테스트 커버리지, 롤백 방법)를 적었다.

**주의**
- evidence는 **악의적 작성자를 막는 장치가 아니라** "재현 테스트가 있다"는 증거를 요구하는 장치다(위조 가능). 진짜 보호는 T2/T3의 사람 승인.
- E2E 같은 무거운 테스트는 evidence 범위에서 제외하고(데모의 결정), 프롬프트로 단위 테스트 재현을 안내.

## 7. 단계 5 — 환류(자기개선)

**목표**: 같은 실패가 반복되면 **규칙(린트/평가 케이스)** 으로 바뀌고, 효과가 숫자로 보인다.

**만들 것(작은 것부터)**
1. **고정 enum의 리뷰 지적 범주**(`error-format|missing-test|security|scope-creep|style|other` 같은 우리 도메인 버전)를 리뷰 JSON에 도입. 런 기록에 `findings`로 저장. **이 단계는 3단계부터 미리 심어 두면 비용이 거의 없다.**
2. **`collect`**(에이전트 아닌 코드): 최근 28일, **서로 다른 이슈 3건 이상**에서 나온 범주만 후보. 열린 개선 PR이 다루는 범주 제외. 이미 병합된 개선 PR 이전의 이벤트는 세지 않음(데모가 겪은 중복 PR 버그).
3. **평가 케이스**(`factory/evals/<slug>/case.yml` + 픽스처): 처음에는 `lint`와 `prompt-contains` 두 종류면 충분.
4. **`eval` 필수 체크**: 모든 PR에서 **기존 케이스가 계속 검출**, 개선 PR에서는 **새 케이스가 base에서 못 잡고 head에서 잡음**.
5. **improve 에이전트**: 수정 허용 경로 4곳(지침, 프롬프트, ESLint 설정, 평가 케이스)만, 허용 밖이면 결과 폐기. **개선 PR은 항상 T3 → 사람 승인.** PR 본문에 삭제된 ESLint 줄을 자동 표기.
6. **주간 리포트 이슈**: 무개입 완주율, 엔진별 성공률·비용, 병합 집중도, 등급별 자동 병합 비율, `needs-human` 사유 상위, 차단기 상태, **규칙 적용 전후 발생 횟수**. 표본 5건 미만이면 비율 대신 "데이터 부족".
7. (후순위) Projects 보드, 대시보드.

**배울 것**: `factory/evals/`, `prompts/improve.md`, `factory-weekly.yml`, `stages/guard.ts`, P4 계획서, 운영 문서의 **"실패 패턴 심기" 리허설**.
**졸업 기준**
- [ ] 의도적으로 심은 실패 패턴이 3개 이슈에서 반복되고, `collect`가 후보로 올린다.
- [ ] 개선 PR이 열리고 `eval`이 "base=못 잡음, head=잡음"을 보고, 사람이 병합한 뒤 **같은 실수를 담은 PR이 lint/eval에서 실패**한다.
- [ ] 주간 리포트에서 규칙 전후 비교가 표본 수와 함께 보인다.

**주의(데모의 교훈)**
- 지침 문장을 지우는 것만으로는 에이전트가 실수하지 않았다 → **리허설 실패는 프롬프트 오염 같은 방식으로 심어야** 할 수 있다.
- 개선 병합 직후 관찰 기간이 0일이면 효과의 근거가 아니다.
- 에이전트가 새 규칙을 추가하며 **기존 규칙을 지울 수 있다**(평가 케이스 없는 규칙은 eval이 못 잡음) → 삭제 줄을 PR에 표기하고 사람이 확인.

## 8. 여러 SaaS로 확산할 때

| 주제 | 제안 |
|---|---|
| 정책 파일 재사용 | SaaS마다 `risk-policy.yml`을 두되 **T3 공통 목록**(워크플로, 에이전트 지침, 정책 자체)은 템플릿으로 공유 |
| 런타임 코드 | 단계 3~5의 CLI를 **한 곳에서 관리하고 각 SaaS repo는 얇게 호출**하는 방식을 검토(데모는 단일 repo 내장). 이 경우 CLI 버전 고정과 T3 취급 필요 |
| 교차 repo 맹점 | 블로그가 지적한 문제. SaaS끼리 의존(공유 라이브러리, 공통 DB)이 있으면 **경계 repo 변경은 T2로** 두고 AI 리뷰에 의존하지 않음 |
| 병합 병목 | 병합 승인자가 나 한 명이면 처리량이 나에게 묶임. **T0/T1 자동 병합 범위를 evidence 이후 넓히는 것**이 유일한 완화책 |
| 비용 | 런 기록의 `costUsd`로 SaaS별·역할별 집계. 처음엔 일일 런 상한을 낮게 |
| 유지보수 중인 레거시 SaaS | 테스트가 없다면 1단계가 길어진다. **버그 수정마다 재현 테스트를 하나씩 쌓는 것**이 evidence 게이트로 가는 가장 현실적인 경로 |

## 9. 하지 말아야 할 것 (원본의 경고에서)

1. **전면 자동화로 바로 가지 않는다**: 데모도 사람 승인 없는 전면 자동화는 "목표가 아니다"라고 범위 밖에 둠. Codex는 이슈→PR 자동화를 철회.
2. **에이전트에게 규칙·게이트·워크플로 수정 권한을 주지 않는다**(T3, Workflows 권한 없음).
3. **LLM에게 병합·상태 완료 선언을 맡기지 않는다**(결정적 코드가 판단·실행).
4. **외부 입력을 프롬프트·이슈에 그대로 넣지 않는다**(격리 태그, 무력화, 정규화).
5. **음성 대조 없이 게이트를 믿지 않는다.**
6. **지침 파일을 여러 개로 분산하지 않는다**(`AGENTS.md` 하나).
