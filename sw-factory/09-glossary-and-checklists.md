# 09. 용어집·진단표·체크리스트

## 1. 용어집

| 용어 | 뜻 |
|---|---|
| 소프트웨어 팩토리 | 요청→구현→검증→병합→배포→실패의 규칙화가 사람의 매번 지시 없이 이어지는 체계 |
| 바이브 코딩 | 사람이 에이전트에게 매번 지시하며 진행하는 상호작용형 코딩 |
| 위험 등급 T0~T3 | 경로 기반 변경 위험 등급. T0 문서, T1 일반 코드, T2 인증·마이그레이션·의존성, T3 팩토리 규칙·워크플로·에이전트 지침 |
| CODEOWNERS | 경로별 필수 리뷰어 지정 파일. T2/T3 사람 승인 강제에 사용 |
| `@factory go` | 쓰기 권한자가 이슈에 남기는 승인 명령. 구현을 시작시키는 유일한 전이 |
| `needs-human` | 자동화가 손을 뗀 상태(사유 코멘트 포함) |
| prepare / agent / publish | 에이전트 단계의 3단 job. 토큰 있는 준비 → 토큰 없는 실행 → 새 토큰으로 재검증·게시 |
| 교차 리뷰 | 구현 엔진과 다른 엔진이 리뷰하는 규칙 |
| `risk-tier` | 변경 경로로 등급을 판정하고 구현 역할의 T3 수정을 막는 필수 체크 |
| `evidence` | 버그 PR의 재현 테스트가 base에서 실패하고 head에서 통과함을 증명하는 필수 체크 |
| `eval` | 평가 케이스가 규칙을 실제로 검증하는지(회귀 방지 + 개선 PR의 새 케이스) 보는 필수 체크 |
| 음성 대조 | 게이트가 막아야 하는 나쁜 입력으로 실제로 막히는지 확인하는 검증 |
| fingerprint | 에러 메시지(정규화)와 스택 상위 3프레임(줄·열 제거)의 SHA-256 앞 16자. 같은 에러를 묶는 키 |
| 런 기록 | `factory-data` 브랜치 `runs/YYYY-MM.jsonl`. 모든 단계 런의 한 줄 기록, 모든 가드레일·보고의 입력 |
| 차단기(circuit breaker) | 최근 7일 implement+fix 10회 이상 & 성공률 50% 미만이면 `FACTORY_PAUSED=true` |
| collect | 최근 28일 실패 이벤트를 범주별로 묶어 서로 다른 이슈 3건 이상이면 개선 후보로 내는 코드 단계 |
| improve | 후보 범주 하나로 규칙·평가 케이스를 만드는 에이전트(허용 경로 4곳) |
| 평가 케이스 | `factory/evals/<slug>/case.yml` + 픽스처. 실패 사례를 박제한 회귀 검사 |
| 3단 승인 모델 | 시작(`go`) / 민감 병합(T2·T3 CODEOWNERS) / 개선 규칙 병합(T3 사람 승인) |
| 판단과 실행의 분리 | 에이전트는 판단하고 되돌릴 수 없는 행동(push, 병합, 상태 완료)은 결정적 코드가 수행 |
| fail closed | 불확실하면 막는다(파일 목록 못 읽음→T3, 계획 없음→실패, 비밀 없음→배포 실패) |

## 2. SaaS 진단표 템플릿

SaaS마다 한 장씩 채웁니다. (예시는 형식 안내이며 실제 값이 아닙니다.)

```markdown
### <SaaS 이름>
| 항목 | 값 |
|---|---|
| 스택(언어/프레임워크/DB) | |
| 저장소 호스팅 / 브랜치 보호 | |
| CI(있음/없음, 소요 시간, 필수 체크) | |
| 테스트(단위/통합/E2E, 대략적 커버 범위) | |
| 배포 방식 / 롤백 방법 | |
| DB 마이그레이션 방식(자동/수동, 롤백 가능 여부) | |
| 민감 영역(인증·결제·개인정보) 경로 | |
| 의존하는 다른 SaaS/공유 라이브러리 | |
| 하루/주당 이슈·PR 수 | |
| 병합하는 사람 수 | |
| 에러·피드백 수집 경로 | |

판별 기준 채점(충족/부분/미충족):
| # | 기준 | 판정 | 근거 |
|---|---|---|---|
| 1 | 작업 유입 자동화 | | |
| 2 | 다중 병렬 흐름 | | |
| 3 | 자동 검증 게이트 | | |
| 4 | 위험 기반 위임 | | |
| 5 | 보고 체계 | | |
| 6 | 자기 개선 루프 | | |

파일럿 적합도(○/△/×): 테스트·CI □ GitHub □ 장애 영향 낮음 □ 내가 코드를 잘 앎 □ 이슈 꾸준함 □
```

## 3. 도입 체크리스트

### 단계 1 — 기반
- [ ] `AGENTS.md` 작성(구조, 명령, 규칙, 마이그레이션 주의, 워크트리)
- [ ] 다른 에이전트 지침 파일은 `AGENTS.md`를 가리키는 링크
- [ ] 검증 한 줄(`typecheck && lint && test`)과 CI
- [ ] 브랜치 보호 + 필수 체크 등록, main 직접 push 금지
- [ ] "테스트 먼저, 버그는 수정 전 실패 테스트 먼저" 지침화
- [ ] 에이전트 PR 1건이 CI 통과, 같은 작업 3회 반복 기록

### 단계 2 — 위험 등급
- [ ] `risk-policy.yml` 작성(좁은 규칙이 위, `default: T2`)
- [ ] T3 목록: CI/워크플로, 에이전트 지침·설정, 정책 파일, 게이트 스크립트, 고정 외부 테스트
- [ ] T2 목록: 인증, 결제, 마이그레이션, 의존성·락파일, 인프라·배포 설정, 시크릿 처리
- [ ] T3 대소문자 무시, rename은 이전·새 경로 모두 판정
- [ ] CODEOWNERS 작성 + 정책과의 동기화 테스트
- [ ] `risk-tier` 체크(base 커밋의 코드로 판정) + 등급 라벨
- [ ] 음성 대조: T3 파일을 바꾼 PR이 막힘, T2 PR이 사람 승인 전 병합 불가

### 단계 3 — 반자동 유입→PR
- [ ] 이슈 템플릿(완료 기준 필수)
- [ ] 트리아지(분류, 중복, 등급 추정, 테스트 가능한 수용 기준)
- [ ] `@factory go|stop|retry`(쓰기 권한 검증, 코드 펜스·봇 무시)
- [ ] 상태 라벨 하나 + 허용 전이표(`merged`/`deployed`는 에이전트 불가)
- [ ] 구현 프롬프트(금지 경로, 의존성 추가 금지, commit/push 금지, 입력 격리 태그)
- [ ] 교차 리뷰(다른 엔진, JSON, head SHA 묶음, 고정 enum category)
- [ ] 수정 라운드 ≤3, 초과는 `needs-human`
- [ ] 3단 job(agent에는 토큰 없음·엔진 키 하나만), GitHub App 토큰, **Workflows 권한 없음**
- [ ] 런 기록 JSONL
- [ ] 예산(턴·시간·비용), 일일 상한, 실패율 차단기
- [ ] 악성 입력 시험(프롬프트 인젝션, 표식 위조, `fixes #N`), 권한 없는 `go` 거부 확인, 차단기 작동 시험

### 단계 4 — 증거 게이트
- [ ] `evidence-plan`(토큰, base CLI) / `evidence`(토큰 없음, PR 코드 실행) 분리
- [ ] base에 테스트 파일만 덮어써서 실패, head에서 통과, JSON 단언 기준 판정
- [ ] `evidence-plan` 실패 시에도 `evidence`가 실패(건너뛰지 않음)
- [ ] 병합 게이트(결정적 코드): T0/T1 + 필수 체크 + head SHA 승인, 변경 파일 못 읽으면 T3
- [ ] PR 보고서 템플릿 + 커밋 트레일러
- [ ] 심은 버그 end-to-end, 수정 전 통과 테스트만 가진 PR이 evidence에서 실패

### 단계 5 — 환류
- [ ] 리뷰 지적 범주 enum + 런 기록 `findings`
- [ ] `collect`(28일, 서로 다른 이슈 3건, 중복 개선 방지)
- [ ] 평가 케이스(`lint`, `prompt-contains`) + `eval` 필수 체크(회귀 + 개선 PR 새 케이스)
- [ ] improve(허용 경로 4곳, 밖이면 폐기, 개선 PR은 T3, 삭제된 ESLint 줄 표기)
- [ ] 주간 리포트(표본 5건 미만이면 "데이터 부족", 규칙 전후 비교)
- [ ] 실패 패턴 심기 리허설 → 개선 PR → 같은 실수가 lint/eval에서 실패
- [ ] (후순위) 보드, 대시보드

## 4. 구현 전 반드시 결정할 질문 (데모의 "판정 후보" 방식 차용)

각 항목마다 **제안 / 근거 / 틀렸을 때 비용**을 적어 두면 나중에 되돌리기 쉽습니다.

1. 우리 SaaS의 T2/T3 경로 목록은 무엇인가?
2. 에이전트 엔진은 무엇을 쓰고 구현/리뷰를 어떻게 교차 배정하나?
3. 런당 예산과 일일 상한은 얼마로 시작하나?
4. 증거 판정에 포함하는 테스트 종류(단위만? E2E는 제외?)는?
5. 에러·피드백 유입을 이슈화할 때 어떤 값을 정규화·삭제하나?
6. 병합 권한자는 누구이고 부재 시 대안은?
7. 개선 규칙의 병합 승인은 누가 하나?
8. 여러 SaaS가 공유하는 코드의 경계는 어느 등급인가?
